# Remaining Useful Life Prediction for Turbofan Engines (NASA C-MAPSS FD001)

MMA3001 — Numerical Methods and Machine Learning · Individual Project

Predicting how many operating cycles a turbofan engine has left, from its sensor history,
to support condition-based maintenance scheduling.

---

## The engineering problem

Jet engines are overhauled on fixed schedules. Replacing a healthy engine wastes remaining
life; missing a failing one risks an in-service failure. Estimating **remaining useful life
(RUL)** from sensor data lets maintenance be scheduled on condition instead.

**Input** — the observed history of one engine: 3 operational settings and 21 sensor channels
(temperatures in °R, pressures in psia, speeds in rpm, flows in lbm/s), one row per flight cycle.

**Output** — predicted RUL in cycles, a non-negative number, for the engine's most recent cycle.

**Scope** — subset FD001 only: simulated data, one operating condition (sea level), one fault
mode (high-pressure compressor degradation). Nothing here establishes behaviour on other
operating conditions, other fault modes, or real engines.

## Results

Single evaluation on the 100 held-out test engines, with every modelling choice frozen beforehand:

| Model | RMSE (cycles) | PHM'08 score | Maintenance cost | Late predictions |
|---|---|---|---|---|
| Baseline — ridge on a single cycle | 21.69 | 1287 | 112 | 58% |
| **Final — gradient boosting on windowed features** | **14.38** | **318** | 58 | 56% |
| Operational — the same model trained at quantile 0.1 | 17.99 | 399 | **23** | **20%** |

The final model reduces test RMSE by 34% and the asymmetric score by 75% against the baseline.
Cross-validation predicted an RMSE of 14.59 against the 14.38 measured on the test set.

The *operational* variant trades 3.6 cycles of RMSE for less than half the maintenance cost and
a drop in late predictions from 56% to 20%. Which model to deploy depends on the relative cost
of a premature overhaul and an in-service failure; see `results/asym_cost_ratios.csv`.

## Repository layout

```
src/cmapss/        library code (see docs/ for the generated API reference)
  loader.py        read and validate the raw files; build RUL labels
  features.py      sensor screening by trend strength; degradation-onset estimation
  windows.py       causal trailing-window features, with edge padding for short engines
  denoise.py       causal per-engine filters: EWMA, rolling median, baseline normalisation
  splits.py        engine-grouped K-fold splits with a leakage guard
  models.py        mean predictor, hand-written ridge, PCA pipeline, boosting factory
  metrics.py       RMSE, MAE, bias, the asymmetric PHM'08 score
  decision.py      maintenance cost model, prediction shift, cost-optimal quantile
  postprocess.py   smoothing predictions along an engine's history
  cv.py            engine-grouped cross-validation and test-set prediction
  profiling.py     timing, FLOP counts, arithmetic intensity, memory, model size

tests/             230 tests (pytest)
notebooks/         01_eda_fd001.ipynb — exploratory analysis and the decisions it supports
scripts/           one script per experiment, each writing to results/
results/           every table and figure cited in the report
docs/              HTML API documentation (generated by pdoc)
data/              the NASA files — NOT committed; see "Getting the data"
```

### Getting the data

The C-MAPSS turbofan degradation data is published by the NASA Prognostics Center of
Excellence as *Simulating Degradation Data for Prognostic Algorithm Development*
(https://data.nasa.gov/dataset/simulating-degradation-data-for-prognostic-algorithm-development).

Place these three files in `data/`:

```
data/train_FD001.txt    100 engines run to failure
data/test_FD001.txt     100 engines truncated before failure
data/RUL_FD001.txt      the true RUL of each test engine after its last observed cycle
```

Scripts accept `--data-dir` if the files live elsewhere; the test suite reads the
`CMAPSS_DATA_DIR` environment variable.

## Running the code

```bash
python -m pytest -v -rs                 # 230 tests
python scripts/run_baseline.py          # ridge on single-cycle features
python scripts/run_windowed.py          # the effect of adding engine history
python scripts/run_gbm.py               # gradient boosting vs ridge (2x2 comparison)
python scripts/run_sweeps.py            # RUL cap and window-length sensitivity
python scripts/run_feature_selection.py # denoising variants, PCA, boosting grid
python scripts/run_asymmetric.py        # cost-aware objectives and the trade-off frontier
python scripts/run_profiling.py         # timing, FLOPs, arithmetic intensity, memory
python scripts/run_final_test.py        # the single held-out evaluation
```

Every script except the last uses **training data only**. `run_final_test.py` is the only one
that scores the held-out test set; its configuration is hardcoded rather than exposed as
command-line options, so it cannot be tuned at run time. `run_baseline.py`, `run_windowed.py`
and `run_gbm.py` retain `--final-test` flags from development; these should not be used now
that the frozen evaluation has been carried out.

## Reproducibility

- All randomness is seeded: fold assignment (`seed=0`, with `0,1,2` used where results are
  averaged over seeds) and `random_state=0` for gradient boosting.
- `run_final_test.py` is fully deterministic and reproduces the published numbers exactly.
- Every number quoted in the report is written to a file under `results/` by the script named
  beside it, so each claim can be traced to the code that produced it.
- The analysis depends on floating-point libraries; small differences across platforms and BLAS
  implementations are possible, though none were observed when re-running.

## Testing

The suite covers the library, not the scripts. Tests are built from small synthetic cases whose
answers are known by construction, rather than from recorded outputs, so they verify behaviour
rather than pin it. Notable categories:

- **Hand-computed values** — metric values, window statistics, RUL labels and cost figures
  worked out by hand and asserted exactly.
- **Causality** — truncating an engine's history must not change any earlier feature, and
  changing a later value must not affect earlier rows. These guard against lookahead leakage.
- **Leakage** — no engine may appear in both sides of any split; a row-level split of the same
  data must be *detected* as leaking.
- **Independent agreement** — the hand-written ridge is checked against scikit-learn to 1e-8,
  and the vectorised trend screening against a plain column-by-column implementation.
- **Validation of the detectors themselves** — deliberately broken implementations were
  substituted to confirm the relevant tests fail, rather than assuming they would.

Tests that need the NASA files skip themselves when the data is absent; run with `-rs` to list
any skips with their reasons.
